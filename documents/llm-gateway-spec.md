# LLM Gateway — спецификация сервиса

Дата первоначальной спецификации: 15.10.2026. HTTP и gRPC gateway реализованы в `services/llm-gateway/` и подключены к backend и course-graph. Тесты с fake upstream не подтверждают совместимость или доступность реальных моделей; эксплуатационные показатели требуют отдельного измерения.

## 1. Задача и границы

Очередь, выбор модели и балансировка LLM-запросов находятся в отдельном сервисе `llm-gateway`. Адреса и число инстансов задаются конфигурацией; транспорт к моделям не зависит от предметных модулей backend.

Название **LLM Gateway** отражает единую точку входа и скрытие инфраструктуры моделей. `LLM Provider` легко спутать с поставщиком самой модели. Альтернатива — `LLM Dispatcher`, если в названии важнее подчеркнуть диспетчеризацию.

### Подтверждено

- Самостоятельный микросервис в этом монорепозитории, очередь на Redpanda.
- Одна прикладная HTTP-операция: OpenAI-compatible запрос без выбора модели клиентом.
- Обязательная сложность: по ней сервис детерминированно выбирает модель, без отдельной router-модели.
- Необязательный boolean срочности: срочный запрос получает приоритет перед ожидающими обычными.
- Более мощный инстанс может исполнять запрос меньшей сложности, если нет ожидающих обычных запросов более высокой сложности; `urgent` имеет приоритет сквозь уровни.
- Параллельная работа с четырьмя существующими развёртываниями; число четыре не зашито в реализацию.
- В v1 только полный ответ; streaming не нужен (согласовано отдельно).

### Ограничения

Непрерывный поток `urgent` может задерживать обычные запросы. В v1 используется один активный диспетчер; возможности и производительность настроенных инстансов подтверждаются отдельными проверками.

В scope нет учебной логики, хранения диалогов, изменения промптов, генерации графа, вызова инструментов, embeddings, мультимодальности, публичного доступа из браузера, дополнительных ручек статуса заданий и автоматического определения сложности. Сервис может передавать только явно поддержанный контракт.

## 2. Термины

| Термин | Значение |
| --- | --- |
| Запрос | Одна операция получения Chat Completion; может ожидать исполнения или выполняться. |
| Сложность (`complexity`) | Оценка требуемой способности модели, которую задаёт вызывающий код; не длина контекста и не срочность. |
| Срочность (`urgent`) | Приоритет начала исполнения, независимый от сложности. |
| Модель | Конкретный идентификатор модели в API upstream. |
| Инстанс | Развёртывание модели с адресом, возможностями и лимитом параллельных запросов. Разные инстансы могут обслуживать одну модель. |
| Пул | Разрешённые для уровня сложности инстансы. |
| Диспетчер | Компонент gateway, который выбирает следующий запрос и резервирует слот инстанса. |

## 3. Контракт HTTP

### Запрос

`POST /v1/chat/completions`, `Content-Type: application/json`.

Gateway доступен только из доверенной локальной сети, клиентская Bearer-аутентификация отсутствует. Токены upstream хранятся отдельно в локальной конфигурации gateway. Клиент не передаёт адрес upstream или его секреты.

```json
{
  "messages": [
    {"role": "system", "content": "Верни JSON с кратким объяснением."},
    {"role": "user", "content": "Объясни разницу между BFS и DFS."}
  ],
  "complexity": "medium",
  "urgent": true,
  "temperature": 0.3,
  "max_tokens": 2048,
  "response_format": {"type": "json_object"},
  "stream": false
}
```

| Поле | Правило v1 |
| --- | --- |
| `messages` | Обязательный непустой массив. Роли `system`, `user`, `assistant`; `content` — строка. Сохраняются содержание и порядок сообщений. |
| `complexity` | Обязательное перечисление `low`, `medium`, `high`. Пропуск, `null` и другие значения — `400`. |
| `urgent` | Необязательный boolean, по умолчанию `false`. Строки, числа и `null` — `400`. |
| `model` | Запрещён, даже если совпадает с конфигурацией. Наличие — `400`. Gateway подставляет upstream `model` сам. |
| `stream` | Отсутствует или `false`; `true` — `400 unsupported_parameter`. |
| `temperature`, `top_p`, `stop`, `presence_penalty`, `frequency_penalty`, `seed` | Необязательные стандартные параметры Chat Completions. Передаются без изменения после проверки типа, диапазона и возможностей пула. |
| `max_tokens`, `max_completion_tokens` | Необязательные положительные целые, одновременно задавать нельзя. Адаптер конкретного upstream проверяет поддержку выбранного поля. Нельзя молча уменьшать бюджет. |
| `response_format` | Необязательный; в v1 `text` или `json_object`. JSON Schema — отдельное расширение после проверки upstream. |
| `reasoning_effort` | Необязательный `low`, `medium`, `high` для совместимости с существующими клиентами. Это параметр генерации, не замена `complexity`. |
| `n` | Отсутствует или `1`. |
| Остальные поля | `400 unsupported_parameter`, включая `tools`, `tool_choice` и мультимодальный контент. Нет молчаливого игнорирования. |

Для параметров, не поддерживаемых ни одним инстансом выбранного пула, вернуть `400 unsupported_parameter` до постановки в очередь. Несовместимый контекст не обрезать; превышение контекстного окна — `400 context_length_exceeded`. Способ подсчёта токенов задаётся адаптером модели; размер HTTP-тела проверяется независимо.

`complexity` и `urgent` удаляются перед отправкой upstream. Gateway не добавляет промпты и не преобразует смысл ответа; из конфигурации к телу добавляются только поля `reasoning_effort_body` инстанса (раздел 4).

Это **совместимость с подмножеством Chat Completions**, с двумя расширениями и без клиентского `model`. Стандартный SDK, требующий `model`, потребует тонкого адаптера; обещания работы любого OpenAI SDK без изменений нет.

### Ответ

Соединение остаётся открытым на время очереди и генерации. Успех — `200` и объект Chat Completion: `id`, `object: "chat.completion"`, `created`, `model`, `choices`, `usage` при наличии у upstream. `model` в ответе — фактически использованная модель. `finish_reason: "length"` сохраняется; gateway не выдаёт такой ответ за завершённый по `stop`.

Заголовок `X-Request-ID` содержит идентификатор gateway и возвращается также при ошибке. Физический инстанс, URL и секреты в ответ не попадают. Успех клиенту отдаётся только после долговечной записи результата в Redpanda.

Не возвращать `202`: отдельного API опроса результата в v1 нет.

### Повторы одного HTTP-запроса

Необязательный `Idempotency-Key` позволяет безопасно переподключиться через ту же операцию. Ключ уникален в пределах учётных данных клиента; без него каждый вызов считается новым запросом.

- Тот же ключ и семантически то же JSON-тело: дождаться существующего задания либо вернуть сохранённый результат/ошибку, без новой генерации.
- Тот же ключ с другим телом, включая другую срочность или сложность: `409 idempotency_conflict`.
- Канонизация JSON исключает влияние порядка ключей; значения по умолчанию нормализуются до вычисления хеша.
- Терминальные результаты и ключи хранятся 24 часа с `FinishedAt`; после этого повтор может стать новым заданием.
- Обрыв HTTP-соединения снимает ожидающего клиента; если он последний, задание отменяется. Правила отмены и восстановления определены в [gRPC-спецификации](llm-gateway-grpc-spec.md), раздел 7.

## 4. Выбор модели и балансировка

`low` — простое извлечение и преобразование; `medium` — обычная генерация и анализ; `high` — сложное рассуждение и проверка. Это ориентиры для авторов вызывающего кода, не автоматические эвристики gateway. Распределение учебных операций по уровням определяется в backend отдельно.

Конфигурация явно сопоставляет каждому уровню сложности непустой список инстансов. Уровни упорядочены `low < medium < high`; инстанс, настроенный для уровня, может исполнять запросы этого и более низких уровней. Например, инстанс `high` совместим с `high`, `medium` и `low`, а `low` — только с `low`. Если инстанс входит в несколько пулов, его уровень обслуживания — наивысший из них; он может брать запросы этого уровня и ниже. Совместимость определяется конфигурацией, а не автоматически выведенными свойствами модели. Все уровни могут ссылаться на одни и те же развёртывания, если это намеренно задано конфигурацией. Нельзя выводить различия в качестве из самого факта наличия четырёх endpoint.

Для каждого инстанса задаются `id`, `base_url`, upstream `model`, ссылка на секрет, `max_in_flight`, поддерживаемые параметры, контекстное окно и таймаут. Необязательный `reasoning_effort_body` добавляет поля тела upstream-запроса для запрошенного уровня `reasoning_effort` — для модели, которая слушается другого параметра (Qwen3 выключает рассуждение `chat_template_kwargs.enable_thinking: false`, а `reasoning_effort` игнорирует). Такие правила для модели хранятся в `services/llm-gateway/config/dev.yaml` под `model_rules.models` по имени upstream-модели: это свойство модели и часть общего runtime YAML. Поле инстанса в `config/dev.yaml` главнее правила модели для того же уровня. Поля добавляются, только если запрос задал этот уровень; они не могут задавать `model`, `messages`, `stream`, служебные `complexity` и `urgent` и параметры, разрешённые клиенту, — такой конфиг отвергается при загрузке. Из допустимых и доступных инстансов выбирается имеющий наименьшее отношение `in_flight / max_in_flight`, при равенстве — с наименьшей ожидаемой длительностью вызова (раздел 5), затем менее мощного уровня, затем round-robin. Лимит общий для всех уровней сложности, использующих инстанс.

Слоты резервируются атомарно до вызова upstream. При четырёх инстансах с `max_in_flight: 1` одновременно исполняются максимум четыре запроса, по одному на инстанс. Значение `1` — безопасная начальная настройка, повышается по результатам измерений.

Если инстансы точного уровня заняты или временно недоступны, запрос может быть исполнен инстансом более высокого уровня по правилам очереди ниже. Запрос никогда не назначается инстансу более низкого уровня. Инстанс с открытым circuit breaker исключается из новых назначений; начальные параметры — три последовательные транспортные ошибки/`5xx`, пауза 15 секунд, затем один пробный запрос. `4xx` клиента breaker не открывают. Вызов, оборванный общим дедлайном задания, не считается отказом инстанса: общий дедлайн включает очередь, и на здоровом инстансе его истечение не открывает breaker (пробная резервация half-open снимается). Breaker открывают только собственный таймаут и отказы инстанса. Итоги вызовов, начатых до открытия breaker, не закрывают и не продлевают его; решение в half-open принимает только пробный запрос.

## 5. Очередь и срочность

Redpanda — долговечный транспорт заданий и состояний. Она хранит упорядоченный лог, а не поддерживает вставку сообщения в его начало. Приоритет реализует диспетчер gateway.

Используется один входной topic `llm.requests.v1` с одной partition и один compacted topic `llm.state.v1`, также с одной partition. Один активный процесс gateway владеет HTTP-входом, потреблением и диспетчеризацией. Внутри процесса исполнения параллельны; Kafka-consumer не привязан к одному инстансу LLM. Горизонтальное масштабирование и автоматический failover gateway не входят в v1; второго активного владельца нужно исключить настройками развёртывания.

Один consumer последовательно принимает задания и регистрирует их в долговечном состоянии. Диспетчер рассматривает все зарегистрированные ожидающие запросы при освобождении любого слота. Повтор с тем же ключом не создаёт новую позицию. Слот не резервируется заранее под локальный пакет запросов.

Инстанс уровня `T` совместим с запросом уровня `R`, если `R <= T` в порядке `low < medium < high`. При назначении свободного слота диспетчер:

1. Рассматривает только ожидающие запросы, совместимые с этим инстансом и поддерживаемые им по параметрам и контексту.
2. Сначала рассматривает все `urgent`, независимо от уровня сложности. Среди них выбирает самый ранний зарегистрированный запрос по offset; поэтому срочный `low` может обойти обычный `high` на свободном `high`-инстансе.
3. Если совместимых `urgent` нет, выбирает обычный запрос с наибольшей сложностью, которую поддерживает инстанс: для `high` это `high`, затем `medium`, затем `low`; для `medium` — `medium`, затем `low`; для `low` — только `low`. Между запросами одного уровня сохраняется FIFO по offset.
4. Если запрос не совместим с этим инстансом либо не поддерживает его параметры/контекст, пропускает его и рассматривает следующий; он не блокирует работу других инстансов.

Когда запрос совместим с несколькими свободными инстансами, выбирается тот, что быстрее его исполнит, а не наименее мощный уровень: иначе одиночные запросы `low` всегда шли бы на самую медленную модель при свободных быстрых:

1. наименьшее отношение `in_flight / max_in_flight`;
2. наименьшая ожидаемая длительность вызова — экспоненциальное скользящее среднее (α = 0,3) фактической длительности upstream-вызовов этого инстанса. В выборку входят успешные вызовы и upstream-таймауты (они ухудшают оценку медленного инстанса); не входят отказы до отправки, отмены клиентом, вызовы, оборванные общим дедлайном задания (замер отражал бы остаток дедлайна, а не скорость инстанса), и ответы `429`. Инстанс без замеров считается самым быстрым, поэтому каждый инстанс получает пробный вызов; оценки живут в памяти и после перезапуска собираются заново;
3. менее мощный уровень;
4. round-robin.

Инстанс, ответивший `429`, `5xx` или упавший на транспорте, «остывает» на время `Retry-After`, а без него — 15 секунд (как пауза breaker): пока он остывает, свободные исправные инстансы выбираются раньше него, даже если у него нет замеров. Если свободен только остывающий инстанс, запрос всё равно уходит на него. Успешный вызов прекращает остывание; таймаут инстанса остаётся замером длительности, отмена клиентом, обрыв общим дедлайном и открытый breaker ничего не меняют. Без этого инстанс без замеров, стабильно отвечающий `429`, сохранял бы первое место навсегда — `429` не открывает breaker.

Порядок выбора запроса для освободившегося слота не меняется: сначала `urgent`, затем обычные по убыванию сложности. Мощный инстанс, занятый простым запросом, не освобождается для пришедшего позже сложного: сложный ждёт освобождения совместимого слота — вытеснения нет.

**Гарантия срочности:** зарегистрированный `urgent` опережает любой зарегистрированный обычный запрос, который ещё не получил слот и совместим с освобождённым инстансом. Срочные между собой идут FIFO независимо от сложности. `urgent` не прерывает уже выполняющийся запрос и не вытесняет его из слота. Запись, ещё не прочитанная из входного topic, пока не участвует в выборе; лаг приёма контролируется отдельно. Абсолютный порядок относительно ещё не зарегистрированных сообщений не обещается.

Непрерывный поток `urgent` может задерживать обычные запросы любого уровня до дедлайна. Без отдельного решения не вводятся aging, квоты срочности или резервирование слотов под обычные задачи.

## 6. Жизненный цикл и восстановление

Состояния: `queued → running → succeeded | failed`; из `queued` возможен `expired`. Повтор после подтверждённого отказа до начала генерации может вернуть задание в `queued` с исходной позицией. Все записи имеют версию схемы, request ID, client ID, idempotency key/hash, исходный offset, время поступления, дедлайн, параметры, номер попытки и выбранный инстанс. Терминальное состояние содержит полный HTTP-результат.

Протокол без дополнительной БД:

1. HTTP-обработчик валидирует запрос и публикует его с `acks=all`; недоступность Redpanda не приводит к обходу очереди прямым вызовом модели.
2. Consumer проверяет идемпотентность и транзакционно записывает `queued` в state topic вместе с commit входного offset. Локальная очередь обновляется только после commit транзакции. Повтор доставки не создаёт второе задание.
3. Перед вызовом модели диспетчер долговечно записывает `running` с идентификатором попытки. Успех этой записи обязателен для начала HTTP-вызова upstream.
4. По завершении записывает `succeeded`/`failed`, затем уведомляет ожидающих HTTP и gRPC-клиентов. Старый результат попытки не может перезаписать терминальное состояние.
5. При запуске gateway восстанавливает последние committed-состояния до зафиксированной границы state topic с `read_committed`; только затем принимает трафик и продолжает входной consumer с committed offset.

State topic ключуется стабильной идентичностью задания; при наличии `Idempotency-Key` она детерминированно включает client ID и ключ. Это позволяет восстановить индекс ключей без отдельного хранилища. Все изменения состояния сериализуются одним владельцем. Для транзакций используется стабильный `transactional.id`, который блокирует записи старого producer; это не заменяет ограничения на число активных gateway и не может остановить уже отправленный LLM-вызов.

После рестарта восстановленные `queued` без активных ожидающих клиентов завершаются как `client_disconnected` до включения диспетчера; повтор с прежним ключом возвращает сохранённый исход. Восстановленный `running` имеет неопределённый исход: upstream мог успеть выполнить запрос. В v1 он завершается `failed / execution_interrupted` и **не запускается автоматически снова**. По умолчанию его слот остаётся занят: клиентские `timeout` и `upstream_timeout` сами по себе не доказывают завершение генерации. Для upstream, где проверено прекращение генерации при закрытии клиентского HTTP-запроса, инстанс может задать `abort_on_disconnect: true`. При этом флаге слот освобождается сразу после любого неопределённого исхода отправленного запроса, кто бы ни закрыл соединение: gateway по своему timeout или дедлайну задания либо модель (EOF, сброс соединения, неполный ответ); после рестарта — при восстановлении прерванной попытки. Клиент получает тот же ответ об ошибке, что и без флага. Настройка действительна только для проверенной версии endpoint вместе с её сетевым путём/proxy и должна быть перепроверена после их изменения. Иначе автоматическое освобождение разрешено только при явно заданном у инстанса `server_execution_limit` — документированном серверном пределе полного выполнения запроса, включая очередь upstream. Поле задаётся строкой длительности; отсутствие или `0s` отключает освобождение по таймеру, отрицательные значения запрещены. Предел должен действовать независимо от разрыва клиентского соединения. Консервативное окно отсчитывается от `FinishedAt` неоднозначного исхода, а для восстановленного `running` — от момента обнаружения прерывания при рестарте. Это сохраняет полное окно для последней попытки после retry/backoff и не включает задержку записи `running` в срок выполнения. У терминальных записей без `FinishedAt` слот по таймеру не освобождается; уже истёкшее окно терминального состояния учитывается при восстановлении. Повтор с прежним ключом возвращает эту ошибку; новый ключ означает осознанную новую генерацию. Клиентские HTTP-соединения после рестарта не восстанавливаются, клиент переподключается сам.

Неопределённая попытка продолжает занимать слот своего инстанса: после ошибки чтения ответа или рестарта нельзя считать upstream свободным только по факту ошибки gateway. Исключение — явно настроенный и проверенный `abort_on_disconnect`, при котором закрытие upstream HTTP-соединения любой стороной прекращает генерацию: слот освобождается сразу после неопределённого исхода. Иначе слот освобождается только по документированному серверному пределу времени генерации либо после операторской проверки. Если ни отмена по disconnect, ни такой предел не подтверждены, автоматическое освобождение по таймеру запрещено. Это правило сохраняется отдельно от терминального ответа клиенту и восстанавливается из состояния попытки.

Гарантия — долговечность ожидающих заданий и дедупликация по ключу в пределах срока хранения. Exactly-once выполнение на внешнем OpenAI-compatible endpoint не гарантируется. При сетевом таймауте нельзя считать, что upstream прекратил генерацию.

Compaction не является TTL. Фоновая уборка публикует tombstone для терминальных состояний спустя 24 часа после `FinishedAt`; незавершённые состояния и терминальные записи с неопределённо занятым upstream-слотом не удаляются по возрасту. Для state topic нельзя включать удаление актуальных записей по времени. Входной topic хранится минимум 7 суток; при превышении допустимого лага readiness снимается, потеря входных offsets не маскируется сбросом на latest.

## 7. Дедлайны, перегрузка и ошибки

Настройки в `services/llm-gateway/config/dev.yaml`: общий дедлайн 180 секунд от поступления в gateway, upstream timeout максимум 120 секунд и не больше остатка общего дедлайна; HTTP-тело до 1 МиБ; до 1000 незавершённых заданий; буфер полезной нагрузки незавершённых заданий до 256 МиБ. Значения конфигурируемые и проверяются под реальной нагрузкой. Retention и лимит размера сообщений Redpanda должны вмещать сериализованное задание и полный результат; превышение лимита результата даёт контролируемый `502`.

Общий дедлайн включает публикацию, ожидание, повторы и генерацию. Клиентские дедлайны и отмена ожидания действуют по [gRPC-спецификации](llm-gateway-grpc-spec.md), раздел 7. Истёкший запрос не начинает новую генерацию. Проверка лимитов незавершённых заданий выполняется последовательно при регистрации, с учётом уже выполняющихся; превышение завершается сохранённой ошибкой `429`. Число HTTP-соединений и незарегистрированных публикаций также ограничено, чтобы очередь не росла через входной буфер.

Gateway сам закрывает простаивающие upstream-соединения через 4 секунды, раньше 5-секундного keep-alive uvicorn у серверов моделей: так вызов не записывается в соединение, которое модель уже закрывает, и не завершается EOF. Значение должно оставаться меньше keep-alive каждого upstream; при добавлении сервера другого типа его перепроверяют.

Автоматический повтор — максимум один, только при доказанном отказе до отправки запроса upstream (например, не удалось установить соединение) либо явном `429` upstream. Учитывается `Retry-After` и оставшийся дедлайн; повтор не занимает слот во время задержки. Таймаут после отправки тела, разрыв во время чтения, произвольный `5xx` и ошибка формата ответа не повторяются автоматически: генерация уже могла состояться.

Ошибки имеют OpenAI-подобную оболочку:

```json
{
  "error": {
    "message": "Превышено время ожидания LLM-запроса.",
    "type": "gateway_timeout",
    "param": null,
    "code": "request_deadline_exceeded"
  }
}
```

| HTTP | Ситуация |
| --- | --- |
| `400` | Невалидный контракт, `model`, streaming, неподдерживаемые параметры, слишком длинный контекст. |
| `409` | Конфликт idempotency key. |
| `413` | Слишком большое HTTP-тело. |
| `429` | Перегрузка gateway или исчерпанные повторы upstream `429`; по возможности `Retry-After`. |
| `502` | Ошибка/некорректный ответ upstream либо `execution_interrupted` после рестарта. |
| `503` | Не готов gateway, недоступна Redpanda, невозможно надёжно принять/сохранить запрос. |
| `504` | Истёк общий дедлайн (`request_deadline_exceeded`, в том числе посреди upstream-вызова) или таймаут исполнения upstream (`upstream_timeout`). Слот после обрыва вызова остаётся неопределённо занят по общим правилам. `upstream_timeout` определяется по причине завершения вызова: если вызов закрыл таймаут инстанса, он остаётся `upstream_timeout` (и считается отказом для breaker), даже когда транспорт сообщил обрыв соединения или неполный ответ. |

При неоднозначном результате публикации или потере соединения клиент повторяет тот же ключ: ошибка транспорта не доказывает, что задание не принято. Ошибки upstream нормализуются, без передачи внутренних URL, токенов и сырых диагностических тел.

## 8. Развёртывание и эксплуатация

Gateway расположен в `services/llm-gateway/`: отдельный Go-модуль, Dockerfile и сервисный Compose. Корневой Compose запускает gateway и Redpanda как зависимости приложения. Gateway не импортирует `internal` backend и не использует предметную БД.

Gateway предоставляет служебные HTTP-ручки `/health/live`, `/health/ready` и `/metrics`. Caddy проксирует весь путь `/llm-gateway/*`, поэтому они доступны и через соответствующий HTTPS-маршрут прокси. Readiness требует загрузки конфигурации, восстановления состояния и доступности Redpanda. Readiness снимается и при неудачной записи состояния, пока gateway не запишет намеченное состояние повторно (согласование): успешного ping Redpanda для возврата readiness недостаточно, новые назначения при этом запрещены, а повтор запроса с тем же ключом после согласования получает сохранённый исход. Подробности — в gRPC-спецификации, раздел «Остановка работы». Работоспособность моделей отражается отдельно: нельзя объявлять их доступными по одному успешному health gateway.

Минимальные метрики: число и возраст ожидающих по сложности/срочности, лаг входного consumer, длительность очереди и генерации, сквозная latency, слоты каждого инстанса, ожидаемая длительность вызова каждого инстанса (`gateway_instance_expected_seconds`), ошибки, retries, таймауты, срабатывания breaker и идемпотентные повторы. Request ID связывает логи HTTP, Redpanda и upstream. В логах и labels нет текстов диалогов, API-ключей и полных тел запросов/ответов.

Поскольку Redpanda сохраняет промпты и результаты, доступ к topics ограничивается ACL, транспорт защищается, диски и резервные копии — по правилам инфраструктуры. Tombstone не гарантирует немедленного физического удаления данных: очистка сегментов и backup retention настраиваются отдельно.

Graceful shutdown: снять readiness, прекратить приём и новые назначения, завершить активные вызовы в пределах grace period и сохранить результаты. Не успевшие закончиться остаются `running` и обрабатываются по правилу восстановления. При потере Redpanda новые генерации не стартуют; уже полученный результат удерживается до сохранения в пределах дедлайна, иначе клиент получает транспортную/`503` ошибку без обещания сохранённого успеха.

Для production Redpanda предполагается replication factor 3 на трёх брокерах; одноброкерный dev-режим не защищает от потери диска. Одна partition не ограничивает LLM-параллелизм, но throughput входного лога и время восстановления нужно измерить. Gateway v1 имеет перерыв обслуживания при рестарте; многорепличный режим требует отдельного протокола владения слотами и ответами.

## 9. Связь с текущим репозиторием

Gateway поддерживает HTTP и gRPC по [отдельной спецификации](llm-gateway-grpc-spec.md). Backend и course-graph обращаются к gateway по gRPC и указывают только сложность. Сохранённые ранее записи с полем `routing_profile` восстанавливаются без него, а новый запрос с этим полем отклоняется как неподдерживаемый параметр. OpenAPI gateway описывает HTTP, protobuf в `services/shared` — gRPC. `reasoning_effort` управляет генерацией, а не выбором пула.

## 10. Критерии приёмки

1. Валидный запрос без `model` возвращает полный Chat Completion; пропуск сложности, неверный boolean, клиентский `model` и `stream: true` отвергаются до вызова LLM.
2. `complexity` и `urgent` не попадают upstream; сообщения и разрешённые параметры сохраняются, upstream `model` берётся из конфигурации.
3. Четыре fake upstream с лимитом 1 одновременно получают четыре запроса; пятый ждёт. Один инстанс, входящий в несколько пулов, не превышает общий лимит.
4. При наличии ожидающих `normal A`, `normal B`, `urgent C`, `urgent D` срочные совместимые C и D назначаются раньше обычных A и B независимо от сложности; между C и D сохраняется FIFO, уже исполняющиеся запросы не прерываются.
5. Обычный `high` назначается раньше ожидающих обычных `medium` и `low` на `high`-инстансе; обычный `medium` — раньше `low` на `medium`-инстансе. Ожидающий `low` может использовать более мощный свободный инстанс, когда у него нет более сложных обычных запросов.
6. `urgent low` может использовать свободный `high`-инстанс перед ожидающим обычным `high`; `urgent` не прерывает уже выполняющийся запрос. Если один запрос совместим с несколькими свободными инстансами, выбирается наименьшая ожидаемая длительность; инстанс без замеров идёт первым; при равных оценках — менее мощный уровень.
7. Занятый инстанс не блокирует совместимые назначения на другие свободные инстансы. Запрос не назначается уровню ниже запрошенного даже при отказе всех подходящих инстансов; он ждёт до дедлайна.
8. Перегрузка ограничивает задания, байты и входные соединения. Дедлайн включает очередь, просроченное задание не начинает вызов модели.
9. Повтор с одинаковым ключом, включая конкурентный, создаёт одну генерацию; другое тело даёт `409`. Повтор после разрыва соединения получает существующий результат.
10. После аварийного завершения `queued` без ожидающего клиента завершаются как `client_disconnected`, `running` не запускаются повторно автоматически, терминальные результаты доступны по ключу до истечения срока. Проверяются сбои до/после каждой границы записи состояния и commit offset.
11. Недоступность Redpanda не приводит к прямому обходному вызову LLM или к выдаче несохранённого успешного ответа. Повтор доставки входной записи не дублирует задание.
12. Потеря одного инстанса исключает новые назначения в него; breaker допускает восстановление. Неоднозначно выполненные генерации не повторяются автоматически.
13. Отдельные тесты подтверждают JSON mode и `reasoning_effort` на реальных endpoint перед переводом существующих клиентов. Fake upstream не доказывает совместимость развёрнутых моделей.
14. Нагрузочный прогон измеряет p50/p95/p99 ожидания и генерации, потребление памяти, backlog и время восстановления. Значения `max_in_flight` и таймаутов подтверждены измерениями; численный SLA до этого не заявляется.

## 11. Основания и альтернативы

- Рекомендуется единый диспетчер с состоянием в Redpanda: минимальное число инфраструктурных зависимостей, но требуется аккуратная реализация транзакций и восстановления.
- Redpanda плюс отдельное хранилище состояний упрощает выбор приоритетных заданий и последующее масштабирование, но добавляет зависимость и согласование двух хранилищ. Это альтернатива, не часть предлагаемой v1.
- Простые Kafka-consumer на каждый LLM-инстанс недостаточны: назначение partitions само по себе не учитывает сложность, доступные слоты и общий приоритет.

Технические основания: [Redpanda: порядок внутри partition](https://www.redpanda.com/guides/kafka-architecture-kafka-partition), [consumer offsets](https://docs.redpanda.com/streaming/current/develop/consume-data/consumer-offsets/), [транзакции](https://docs.redpanda.com/streaming/25.3/develop/transactions/), [compaction и tombstone](https://docs.redpanda.com/streaming/current/manage/cluster-maintenance/compaction-settings/), [OpenAI: Create chat completion](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create). Документация OpenAI задаёт форму API, но не подтверждает поддержку параметров четырьмя развёртываниями команды.
